## v8.357 · 档位覆盖:不要用高档模型做底智商任务(用户拍板)

> 起因 case(aon-main DEV-F260910162653):用户问「你做测试用的是什么模型」,那边 AI 答「实现路继承 Fable 5.1 · 验证档任务用 sonnet · 正式测试证据另派 sonnet」—— **完全合规**(白名单本来就写着「执行测试 · 单测 · 集成测试 · e2e」降验证档)。用户接连拍板:「涉及测试的都降档」→「测试和验证类任务都要降档」→「**你全局检查下,不需要用高档模型做底智商任务**」→「ship 也用验证档模型」→「micro 默认使用执行档」。
> 🔴 **载体归位**:那边的 AI 把拍板写进了项目级 memory(`~/.claude/projects/<项目>/memory/`)—— 模型分档是**框架级**规则,写进项目 memory = 换个项目就失效,下个项目的 AI 还会把同样的问题再问用户一遍。

### 全局扫描查出的缺口(不是「没写规则」,是**规则没覆盖到的面**)
- ① **白名单只管「派发时定档」,管不到已派出的执行型 agent 内部做什么** —— 实现路继承主模型,却在里面跑**全量 vitest + 变异验证** = 拿深度档干机械活。技术上实现 subagent 不能中途换模型 → 只能划边界:实现路只跑**与本路改动直接相关的最小自测**(保住 TDD 红绿循环不跨 agent 往返),**全量套件 · 变异验证 · 基线指纹采集 · `xx-complete` 正式证据 → 一律另派验证档**。
- ② 🔴 **`test-stage` 零档位声明**(`browser-e2e` 有、`test` 没有)—— 整个 stage 就是「把『实现说它好了』变成机器可验的通过证据」,却默认继承会话主模型。**最大漏口**。
- ③ **`execute-stage` 零声明** —— micro 的准入白名单已经把改动卡死成零逻辑变更(文案/样式/资源/配置常量/注释),**门槛最低的 stage 反而没有档位约束**。
- ④ **`ship-stage` 零声明** —— push / MR / 合入监控 / CI 日志拉取与归因 / worktree 清理 / 归档誊抄,全是搬运活。
- ⑤ 🔴 **一处真冲突**:白名单写「**冷审执行**」降验证档,而 goal/blueprint 写「**冷审**必用主模型 · 不许降到验证档」—— 两条硬规则直接打架。

### 变更
- **白名单正名**「**测试与**验证类白名单」(原名让人以为不管「测试」· 同 §Out of Scope 与限制 / §查询性能与数据量 的正名问题)+ 补齐 **变异验证 · 全量套件跑批 · 基线/指纹采集 · 覆盖率统计**。
- **定档判据换成可判问句 · 三档各一句**(原「校验/枚举型 vs 判断/创造型」仍是**形容词式分类**,分不了界,且「执行」档在判据里根本没出现):① **照着已有清单核对** → `验证`;② **按既定方案把东西写出来** → `执行`;③ **要想出清单上没有的东西** → `深度`(不许降)。❗ **换个便宜模型产出不会更差的,就没有理由用贵的** —— 会话主模型是为了跟你对话选的,不是为了跑测试和改文案选的。
- **修 ⑤ 的冲突**:白名单「冷审执行」→「**冷审验证轮**(Round 2+ 核实上轮 finding 修没修)」· 明写「**首轮全量冷审属判断型,不降**:它要找的是没人想到的东西」。两侧口径就此一致。
- **逐 stage 补档位声明**:`test`(整 stage 测试与验证类)· `ship`(用户拍板 · 🔴 **保留一个例外**:CI 红归因到本 feature 后**要改代码**那段是实现活,按实现路的档走)· `execute`(**执行档** —— 用户拍板;micro 改的是文案/常量,但那仍是「**写出来**」不是「照着清单核对」,按判据归执行不归验证)· `dev`(内联边界 + 「测试节奏 AI 自定,但**模型档位不自定**」)。
- **判断型三个 stage 确认不加降档**:`diagnose`(根因排查)· `ui-design`(设计)· `pm-acceptance`(产品视角验收决策)—— 降档会直接伤产出。

### §查询性能 → §查询性能与数据量(实证 case)
> case:报表接口 staging 13–19s。BQ 查询 **1 秒**完成,但 5.64 万行 × 11 字段展开成 **45.3MB JSON** 传回、解析、深拷贝、再解码,跑在 **0.2 核**上。
> 🔴 旧表的四项判据(索引命中 / 无全表扫 / 无 N+1 / 已分页)在这个 case 里**全绿**,结论「够快」属实 —— **不是漏填,是问错了问题**:它只问「查询快不快」,不问「结果搬多少回来」。查询快 = 这一步快,这个前提在单机 OLTP 里大致成立,在 OLAP/跨进程数据源里根本不成立。

- 正名 + 触发条件从「涉 SQL」扩到「**涉批量数据读取**」(BQ/ES/Mongo/HTTP 批拉同形状)· 标题内写死「**查询 + 搬运两段都算**」;
- 新增**搬运量比值**列(**算出来不是判断出来**):「调用方最终要多少 vs 搬回来多少」—— 差 **≥2 个数量级 → 这是架构问题不是优化问题**,必须回答「聚合为什么不能下推到数据源」;
- **兜底 ≠ 够快**,判据一句话:**这条理由是在说「它跑得动」,还是在说「跑不动时不会炸」?** 超时/分页/费用上限/连接数上限都是后者 —— 它们写进 TECH 后**读起来最像「性能已经考虑过了」**;
- **「够快」必须带规格**:差 ≥1 个数量级(本地多核 vs 容器 0.2 核)结论即不成立 —— 🔴 只落 TECH 侧不铺到 test:性能账要在方案阶段**算**出来,等 test **测**出来架构已经定型。

## v8.354 · 需求简洁性的减法侧:限制必要性(用户拍板)

> 用户:「我们是否有 PRD 需求简洁性的评审约束,例如不要扩展没必要的功能,不要做没必要的限制。」
> 查证结果**一半有一半没有**:**加法侧**(别扩展没必要的功能)有三层挡 —— goal 规则 6.5 功能优先·复杂度守恒(「更简的需求形态达成同等业务价值」永远合法)· PL 质疑六问③范围最小化 · PRD 起草思考规范;**减法侧**(别做没必要的限制)搜遍 `stages/ roles/ templates/ standards/` **零命中**。
> 🔴 **这不是漏写,是结构性盲区**:PL 的 mandate 是把范围**往下压**,所以加法天然有对抗角色、减法没有 —— 而**限制读起来永远像「最小范围」**,越保守越显得克制,越没人替你质疑。
> 🔴 **代价还不对称**:多做一个功能 = 浪费工时(起草/评审当场看得见)· 多加一条限制 = **用户真想做的事做不了**,而且要到上线才发现 —— 与 v8.350 的范围收窄同一族病:PRD 完全自洽,下游全在认真实现一个被我自己收紧的范围。

### 变更
- **判据一句话**(与 v8.352 生效闸同构 · 形容词不可判、问句可判):**这条限制是「业务真要求的」还是「我加的」?** —— 「我加的」→ 要么写出**不加会出什么事**,要么**去掉这条限制**。
- **载体复用 v8.350 那张表**(不新增节 —— PRD 瘦身门只剩几行余量 · 双载体必漂):§Out of Scope → **§Out of Scope 与限制**,同表收「不做的事 / 加的限制」;「性质」列两族取值(排除:技术限制 / 🔴 我的解释 · 限制:业务真要求 / 🔴 我加的),末列对「我加的」收**不加会出什么事**。
